# datatable-axios Modernization Plan

Bring `datatable-axios` up to the same project structure, tooling, and
quality bar as `niftycli` (currently v1.8.0, actively maintained). Scope is
**structure and tooling only** — the public API (`get`/`post`/`put`) stays
behavior-identical; no breaking redesign.

Reference project: `/home/mahmudun-nabi-kajal/Workspace/Personal/niftycli`
Target repo: `/home/mahmudun-nabi-kajal/Workspace/Personal/datatable-axios`
(existing git repo, remote `git@github.com:mahmudunnabikajal/datatable-axios.git`)

Docs repo: `/home/mahmudun-nabi-kajal/Workspace/Personal/datatable-axios-docs`
(already created as a raw clone of `niftycli-docs` — still contains
niftycli's CLAUDE.md, gif-generator, and website content; needs rebranding).

---

## 1. Current state of datatable-axios

- `package.json` v0.0.11, `type: module`, built with **Rollup** (esm/cjs/umd
  outputs), peer-deps on `axios`.
- `src/`: 3 files — `axios.js` (sets `window.axios` global), `datatable.js`
  (class with `get`/`post`/`put`, reads pagination params off
  `window.location.search`), `index.js` (re-export).
- No tests. No linting/formatting config. No CI. No CHANGELOG. No semantic
  versioning automation — versions bumped by hand in commits like `6842c9b
0.0.11`.
- `docs/` is a single static `index.html` (GitHub Pages), not a real docs
  site.
- Browser-oriented: assumes `window` exists (no Node/SSR support), which is
  a real constraint carried over from the current API — not something this
  pass will change per your scope decision.

## 3. package.json changes

Add scripts (mirroring niftycli's naming so muscle memory transfers):

```jsonc
"scripts": {
  "build": "rollup -c",
  "test": "node --test",
  "test:coverage": "node --test --experimental-test-coverage --test-reporter=lcov --test-reporter-destination=lcov.info",
  "lint": "eslint .",
  "lint:fix": "eslint . --fix",
  "format": "prettier --write .",
  "format:check": "prettier --check .",
  "update:deps": "npx npm-check-updates -i --format group",
  "prepublishOnly": "npm run build"
}
```

Add devDependencies: `@eslint/js`, `eslint`, `eslint-config-prettier`,
`eslint-plugin-prettier`, `globals`, `prettier`, `semantic-release` +
`@semantic-release/{commit-analyzer,git,github,npm,release-notes-generator}`.

Drop the old hand-rolled `"publish": "npm run build && npm publish"` script
— semantic-release's npm plugin takes over publishing.

## 4. Testing

- No browser test runner needed if we mock `window`/`axios` — Node's
  built-in `node:test` (same as niftycli) works via a minimal `happy-dom`
  or manual `globalThis.window` stub, since `datatable.js` reads
  `window.location.search` and `window.axios`.
- Cases to cover: GET/POST/PUT without query params, GET/POST/PUT with
  page/paginate/search params, URL-building correctness.
- Wire into `sonar.yml` the same way as niftycli's `test:coverage` step.

## 5. CI / release automation

- Copy `publish.yml` and `sonar.yml` from niftycli almost verbatim; swap
  Node version if datatable-axios needs to support older Node/browser
  consumers (no reason to require Node >=24 for a browser lib — recommend
  Node 20 LTS for the CI runner only, unrelated to the library's own
  runtime which is the browser).
- Copy `.releaserc.json` verbatim — same semantic-release plugin chain.
- Requires the same repo secrets as niftycli: `NPM_TOKEN`, `SONAR_TOKEN`
  (GITHUB_TOKEN is automatic).

## 6. Linting/formatting

- Copy `eslint.config.js` and `.prettierrc.json`/`.prettierignore`
  verbatim. One difference: add `globals.browser` (not `globals.node`)
  since this library runs in the browser and references `window`.

## 7. What stays the same (explicitly out of scope)

- Public API: `datatable.get/post/put(url)` signature and behavior.
- Rollup as the bundler and its three output formats (esm/cjs/umd).
- The `window.axios` global-setup pattern in `src/axios.js`.
- No TypeScript conversion, no Node-target support, no new HTTP verbs —
  none of that was asked for; can be a later, separate proposal.

## 9. Node engines field

**Leave unrestricted** — no `engines` field added to `package.json`.
Rationale: this is a browser library consumed through bundlers (Vite,
Rollup, webpack, etc.), not run directly under a Node runtime, so gating
on Node version (as niftycli does for its CLI) doesn't apply here.

## 10. CHANGELOG.md backfill

Backfill full history for 0.0.1–0.0.11 from git log + npm publish
timestamps before semantic-release takes over, and the **next release
after this modernization work lands is `1.0.0`** (not a semver-auto patch)
to mark the structural relaunch. Concretely:

1. Write `CHANGELOG.md` by hand covering 0.0.1 → 0.0.11, using the
   Keep-a-Changelog format, one section per version, dated from npm's
   publish timestamps (0.0.1 2023-08-20 → 0.0.11 2023-09-07, per `npm view
datatable-axios time`) and summarized from the corresponding git log
   commit ranges between each version-bump commit.
2. Add a `## [1.0.0]` section for the modernization release itself
   (tooling/CI/testing/structure changes — no API changes) once it ships.
3. After that, `.releaserc.json`'s `@semantic-release/git` +`release-notes-generator` plugins take over CHANGELOG.md maintenance
   automatically — no more manual edits.
4. Because 1.0.0 is a deliberate manual version choice rather than
   whatever semantic-release would compute from Conventional Commits, the
   first release will need either a manual npm version bump to `1.0.0`
   before enabling the automated pipeline, or a `"branches"` conditional
   release note — simplest is to hand-set `"version": "1.0.0"` in
   `package.json` once, commit it as `chore: relaunch as 1.0.0`, tag it,
   and let semantic-release compute versions forward from there.
